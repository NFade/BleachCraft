## 1. Что сделано

- `tp.swordScale` (умолчание 1.25) множит размер меча в руке, в блоке, в держании и ножен: на бедре и едущих с мечом в запечатанном блоке. Эффективный масштаб меча 1.6 * 1.25 = 2.0, ножен 1.6 * 1.25 = 2.0. Допускается `tp.swordScale.<id>` (`senbonzakura`, `sode_no_shirayuki`).
- Где живёт: секция `"tp"` в `config/reiatsu_test_client.json` (новый `client/model/TpConfig`: при первом старте пишется `"tp": {"swordScale": 1.25}`, файл перечитывается раз в секунду, кривое значение даёт умолчание, непарсящийся файл не перезаписывается, диапазон 0.5..2.5). Необязательные ключи: `swordScale.<id>`, `guard.shift` [x, y, z] px. Они не пишутся, чтобы старый файл не прятал будущие умолчания (T0). Dev `pose_override.json` секция `tp` по-прежнему главнее.
- Как масштаб доходит до игры БЕЗ правки JSON дисплея: `TpPose.Input.swordScale` -> эффективные масштабы кадров. Решатель выдаёт поправку предмета `G` (`gT`, `gQ`) и теперь её равномерный масштаб `gS` (= swordScale); `BcItemPose` применяет `translate(gT) rotate(gQ) scale(gS)` перед дисплеем. При ударе Better Combat (когда `G` гаснет) меч растёт вокруг точки хвата (`pivot 0,-2,1.75`) на тот же множитель (`TpPoseDriver.strikeScale`, с весом удержания). Почему не JSON: `models/item/*_display.json` `thirdperson_righthand` один для обоих лиц инвентаря/земли/без позы (броня-стойка, плавание, падение) и читается в `TpPoseDriver` как «дисплей»; правка JSON изменила бы эти состояния и поломала бы инвариант `G` и тесты. В состояниях без позы (стойка с бронёй, плавание, полёт) меч и ножны остаются 1.6, переход смягчается весом удержания 0.15 с (у ножен резкий, они рисуются по кадрам решателя либо старым путём).
- Привязанные к 1.6 константы стали функциями масштаба (`TpPose.scaleRatio/tsubaPx/pommelPx/fistR/fistL`, умножение на `scale / 1.6`): `TSUBA_PX`, `POMMEL_PX`, `C_R`, `C_L` (старые константы остались значениями при 1.6), `GUARD_C_L`, хват левой руки на ножнах `saya.c` (4.5 px) и `sealed.c_r`. Положения кулаков в px по руке неизменны, а места на рукояти растут вместе с мечом.
- Ножны растут вокруг устья: `hipFrame(hip, ks)` сдвигает центр ножен назад вдоль направления на `(ks - 1) * 1.7 px`, так что устье остаётся там же (смещение центра 0.43 px при 1.25), ножны не уходят в тело. Рамка ножен совпадает с рамкой меча в запечатанном блоке (`saya == sword`).
- Меч в блоке растёт вокруг точки цубы пользовательского меча (-3.9, 5.9, -6.1) px (`GUARD_TSUBA_POINT`): центр хвата = точка цубы - `tsubaPx(масштаб)` вдоль клинка + сдвиг. Ключ `guard.pos` (dev) остаётся абсолютным.

## 2. Сдвиг меча в блоке

Критерий (из плана): оба кулака на рукояти, между навершием и цубой (центры не ближе 0.4 k к концам), расстояние между кулаками вдоль клинка от 1.5 k до 4 k, не дальше 2.2 px от оси (тест требует 2.5); k = масштаб / 1.6; руки (GUARD_ARM_R/L) авторские и НЕ менялись, углы рук не правились.

Поиск: перебор по сетке 0.05 px в кубе +-3 px, минимальная длина сдвига при выполнении критерия для широких и тонких рук. Результат `GUARD_SHIFT = (+1.45, -0.35, +0.55)` px в системе тела (x к ЛЕВОМУ боку персонажа, это правее на экране при виде спереди, как просил пользователь; y вниз, z назад к телу). Длина 1.59 px, из них 1.02 px вдоль клинка к острию и 1.22 px поперёк. Для левши зеркально. Чистое смещение центра хвата относительно прежнего (с учётом роста вокруг цубы): (+1.23, +0.02, +0.57) px; точка цубы сдвинулась ровно на `GUARD_SHIFT`. Подобран для масштаба 2.0; критерий проверен тестом также для 1.92 и 2.08.

### Положение кулаков вдоль рукояти до/после (px от центра хвата, правша; левша те же числа)

Обозначения: along = вдоль клинка (положительное к острию), off = расстояние от оси. Сторона «до»: масштаб 1.6 без сдвига (цуба 1.7, навершие -4.9). «После»: масштаб 2.0 со сдвигом (цуба 2.125, навершие -6.125).

| Руки | кулак | до: along / off | после: along / off |
|---|---|---|---|
| широкие | правый (меч) | -0.415 / 1.079 | -1.009 / 0.996 |
| широкие | левый | 2.205 (за цубой) / 3.258 | 1.612 / 2.038 |
| тонкие | правый | -0.634 / 1.479 | -1.227 / 0.632 |
| тонкие | левый | 1.685 / 3.400 | 1.092 / 2.182 |
| расстояние между кулаками вдоль клинка (широкие / тонкие) | | 2.62 / 2.32 | 2.62 / 2.32 (нужно 1.88..5.0) |

То есть левая рука раньше стояла за цубой и в 3.3 px от оси (отсюда «держит одной рукой»), теперь на рукояти под цубой в 2.0 px.

Для справки, держание и запечатанный блок (по формулам масштаба): правый кулак -0.8 px -> -1.0 px, левый -2.4 -> -3.0, левая рука на ножнах 4.5 -> 5.625.

## 3. Эффекты, привязанные к клинку (проверка на жёсткое 1.6)

Поиск по `1.6` и по именам руки/острия в `client/` и `main/`:
- `BladeFlights`, `RukiaServerFx` (сервер): точки от глаз игрока (`getEyePos`), от модели меча не зависят.
- `ScabbardRenderer`: рисует по кадрам решателя (масштаб внутри кадра). Путь без позы (`renderHip` для не-игроков) использует манифест 1.6, это сознательно (меч в руке там тоже 1.6).
- `KidoFx.hand`, `CageFx.handOf`, `SwarmMath.hand`: приближённые координаты руки по рысканью, без длины меча.
- `MeleeTrailFx`/`MeleeTrailMath.REACH = 1.85` (плечо до острия, свободная константа, ключ `fx.meleeTrail.reach`): не выведена из 1.6, оставлена. При масштабе 1.25 меч на четверть длиннее, при желании поднимите `fx.meleeTrail.reach` примерно до 2.2.
- `BcItemPose.POS (0, -1.05, 0.18)` (сдвиг при ударе, считан для 1.6) не пересчитывался: цуба при ударе на ~0.4 px дальше от кулака. Влияет только на удары BC. Пересчитать, если на видео заметно.
Остальные совпадения «1.6» в FX не связаны с мечом.

## 5. Тесты

`TpPoseTest` 11 -> 15 тестов; все старые идут по трём масштабам (коэффициент 0.625, 1.0, 1.25 при дисплее 1.6 = эффективные 1.0, 1.6, 2.0): `heldSwordLandsOnItsFrame` (цепочка теперь с `gS`), `handsReachTheirPointsOnTheSword`, `sealedSits...` (функции масштаба), `heldSwordIsUpright...`, `blockCarries...AndTheEdgeForward`. Новые:
- `blockPutsBothFistsOnTheHilt`: критерий выше для коэффициентов 1.2, 1.25, 1.3, оба лица рук, обе руки, p = 0 и 1 (плюс запас 0.4 k и 2.2 px для 1.25).
- `withoutTheShiftTheLeftFistWasBesideTheHilt`: пин «до» (2.205 / 3.258 / -0.415 / 1.079).
- `theSwordScaleFactorIsTheSameAsALargerDisplayScale`: инвариантность: дисплей 1.6 с коэффициентом 1.25 даёт те же кадры меча и ножен, руки и цели, что дисплей 2.0 с коэффициентом 1 (при сохранении устья ножен).
- `fistPlacesAlongTheHiltScaleWithTheSword`: места кулаков в единицах масштаба не зависят от масштаба (допуск 1e-6), устье ножен неподвижно, острие над землёй.
Исключение при масштабе 1.0: проверка «зазор под цубой» и «навершие ниже левого кулака» выполняется только при масштабе не меньше 1.6 (кулак 4 px больше рукояти 4.1 px), на 1.0 проверяется, что центры кулаков лежат на рукояти.
