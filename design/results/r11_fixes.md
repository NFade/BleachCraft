# R11: исправления по ревью (r11_review_findings.md). Код и тесты готовы, в игре НЕ проверено

Ветка `r11-fixes` (база ca889a0), ничего не закоммичено. `./gradlew build` зелёный, 1275 тестов, 0 падений (новых около 37). Игру не запускал. Всё поведение в игре UNVERIFIED.

## 1. Стена Рукии висит или с дырами в траве поля мороза: ИСПРАВЛЕНО
- Подтверждено чтением кода: `FROST_SPRIG` не `replaceable()`, без коллизии, `WorldProbe.passable` его не считал свободным, а `support` не считал опорой, `floorY` возвращал `NO_GROUND`, стена висела на высоте луча; клетки со ростком `placeWall` отвергал.
- Новый `server/SoftPlants` (общий список мягкой растительности: росток мороза, трава, высокая трава, папоротники, мёртвый куст, ростки Незера, малые и высокие цветы). `TempBlocks.wallReplaceable` теперь принимает их, поэтому и поиск пола (`IceWall.WorldProbe` вызывает ту же функцию), и `placeWall` ставят блок стены в такие клетки. Цветы вне поля мороза тоже считаются свободными (в ванили они не `replaceable`).
- Чтобы не сломать журнал мороза: поверх ростка стена запоминает `air` (оригинальную траву хранит журнал `FrostField`), а `FrostField.restoreOne` теперь принимает и блок `ice_wall` как «свою» клетку (оттаивание раньше исчезновения стены не теряет траву; собственное восстановление стены видит изменённую клетку и не трогает её). Использован `IceWall.isWall(cur)`, чтобы не задеть пин `FrostBlocksSourceTest` («Blocks.ICE» в `FrostField.java` запрещено).
- Тесты: `IceWallLayoutTest` +2 (слой растений: пол найден, нет дыр; зеркальный случай документирует старое поведение), `IceWallSourceTest` +1.
- UNVERIFIED: в игре на траве с цветами в банкае. Ожидается строка лога `wall at ... base N` без `(no ground, at the aimed height)`.

## 2. Пульсы BankaiField платят Rage: ИСПРАВЛЕНО
- Подтверждено: `hurtPlain(INDIRECT_MAGIC)` с кастером-атакующим попадал в ветку `isAbilityDamage`.
- Новый `Targeting.hurtUnrewarded` (как `hurtPlain`, плюс отметка на время вызова `damage`), `RageManager.beginUnrewarded/endUnrewarded` (счётчик глубины, один серверный поток, AFTER_DAMAGE и AFTER_DEATH идут внутри `damage`). Пульс не платит ни награду за способность, ни «dealt», не расходует взведённую награду каста, не засчитывает убийство. Кидо остаётся на `hurtPlain` и платит (так задумано). Чистая политика: `core/rage/RageReward.classify`.
- Тесты: `RageRewardTest` (4, включая проверку, что поле вызывает `hurtUnrewarded`, а кидо нет).

## 3. /reiatsu reload не применяет kido в живых машинах: ИСПРАВЛЕНО
- Подтверждено: `StateMachine.kidoCfg` ставился только в `createSession`.
- `KidoManager` в обратном вызове reload вызывает новый `ZanpakutoManager.refreshKido(c)` (цикл по сессиям, `setKidoConfig`). Уже запущенный gap и кулдауны не пересчитываются задним числом (идут по старым числам до конца), новые касты берут новые cost, cooldown, gcd, enabled.
- Тесты: `KidoCastTest` +1 (новая конфигурация на живой машине), `R11ReviewFixesSourceTest` (проводка).

## 4. HUD берёт стоимости Rage и минимум шикая из умолчаний: ИСПРАВЛЕНО
- Подтверждено: три места в `HudModel` использовали `RageConfig.defaults()`.
- Новое вложение `reiatsu_test:rage_tuning` (`RageTuningData`: shikaiCostTenths, bankaiCostTenths, bankaiMinShikaiTicks; только владельцу, не сохраняется), сервер пишет его в `RageManager.sync` каждый тик, когда значение отличается (после reload за тик). Протокол `RageData` и пакеты не менялись, добавлен только новый тип вложения (клиент и сервер из одного джара). Чистая часть `core/rage/RageTuning` (стоимость, оставшееся время шикая, «хватает ли Rage на банкай», секунды для тоста с минимумом 1). `HudModel` и `ClientState.rageTuning()` используют её; до первой синхронизации действуют умолчания.
- Остаётся: `stateChangeAt` клиента отсчитывается от времени получения состояния, камень может опережать или отставать на задержку (на решение сервера не влияет).
- Тесты: `RageTuningTest` (6).

## 6. ice_wall после краша: ИСПРАВЛЕНО
- Подтверждено: у `FrostField` есть орфанная зачистка при загрузке чанка, у стены не было.
- `TempBlocks.init()` (вызывается из `ZanpakutoManager.init`) регистрирует `ServerChunkEvents.CHUNK_LOAD`: в секциях, где в палитре есть `ice_wall`, каждый блок без записи в журнале заменяется воздухом (лог `[tempblocks] chunk ... removed`). Защита `restoring` вокруг каждого восстановления (чтение клетки может загрузить чанк, у которого запись уже вынута из журнала), плюс проход по уже загруженным чанкам вокруг спавна после отката остатков при старте сервера (как у мороза). Блок `ice_wall`, поставленный командой `/setblock`, при следующей загрузке чанка тоже исчезнет.
- Тесты: `R11ReviewFixesSourceTest` (источниковый), чистая логика журнала `contains` уже покрыта `TempBlockJournalTest`.

## 7. GrassGuard шире травы: ИСПРАВЛЕНО на серверной стороне
- Подтверждено: правило «без коллизии и твёрдость 0» защищало факелы, пшеницу, тростник, саженцы, красный камень.
- `SwingThruRules.shouldSwing(holds, softPlant, noCollision, hardness)` получила параметр `softPlant`; `GrassGuard` передаёт `SoftPlants.isSoftPlant(state)`. Факелы, посевы, сахарный тростник, редстоун-пыль, саженцы, ягодный куст, тросовая растяжка теперь ломаются мечом как обычно. «Ростки» понял как росток мороза (`FROST_SPRIG`) и ростки Незера; ванильные саженцы НЕ включены, скажи, если нужны.
- Клиент (`BcGrassSwing`) не менялся: он переключает режимы Better Combat, а что BC считает «травой» при клике, решает сам BC (мной не проверялось). Если BC замахивается сквозь факел, левый клик по нему останется замахом, а не ломанием; это надо проверить в игре.
- Тесты: `SwingThruRulesTest` (6, был 4; обновлены под новую сигнатуру, добавлены «не растение» и проверка списка).

## 8. Конфиги: запись, блокировка, миграция клиента: ИСПРАВЛЕНО
- Подтверждено: `Files.writeString` усекал файл; `migrateClient` нигде не вызывался; загрузчики серверного файла не синхронизировались между собой.
- Новый `core/config/ConfigFileIo`: `writeAtomic` (временный `*.tmp` и `Files.move` с ATOMIC_MOVE, запасной вариант `REPLACE_EXISTING`), `lockFor(path)`, `migrateFile` (штамп, одноразовая копия `.bak_vN`, нечитаемый файл не трогается). `ModConfig`: все записи через `writeJson`, все загрузчики и `migrate` `synchronized` на классе. - Тесты: `ConfigFileIoTest` (10: атомарность, неудачная запись не портит файл, замок, параллельные циклы без потерь, миграция клиента сохраняет все ключи, нечитаемый файл, текущая версия).

## 9. Поза (`tp.*`): ИСПРАВЛЕНО (кроме спорного пункта про порядок)
- Подтверждено: любой ключ клиентского файла шёл в позу без ограничений (только `swordScale` и `guard.shift`), а `vec` отдавал первые 3 числа даже для шестичисловых `guard.arm_*`.
- Новый `core/combat/TpKeyLimits`: таблица пределов для каждого ключа, который читает `TpPose` (тест сверяет таблицу с исходником решателя), векторы по длине и покомпонентно; неизвестный ключ секции игнорируется, ничего не стирается. `TpConfig.num/vec` идут через неё. `TpPose.solve` теперь заменяет масштаб дисплея или ножен 0, отрицательный, NaN на опорный 1.6, NaN-масштаб меча на 1.0 (деление на ноль в `handPoint` и `quat`). Всё равно `TpConfig.load` теперь сам создаёт файл с секцией и штампом, если его нет, поэтому порядок загрузчиков больше не важен.
